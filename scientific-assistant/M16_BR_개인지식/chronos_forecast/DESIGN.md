## 0. 한 줄 요약

지금은 **"임계값을 넘으면 경보"**(반응형)다.
바꾸려는 건 **"몇 분 뒤 임계값을 넘을 것 같으면 미리 경보"**(선제형) + **"예측이 불확실하면 함부로 안 울림"**(가드레일)이다.

- **예측**: Chronos-Bolt (Amazon, 오픈소스 Apache-2.0) 가 핵심 정체 신호를 N분 앞서 확률 예측
- **행동(가드레일)**: 예측 분포 → 경계 있는·인과적 stage/위험도 판정. 업로드하신 *TightLoop Sentinel*이 하는 "역할"을 우리가 직접 구현

## 1. 지금 시스템(AS-IS)과 실패 모드

### 1.1 현재 구조
`hubroom_predictor.py` (1,495줄)는 매 1분마다 8개 영역(M16HUB/M14/M14B/M16A/M16B/M16/M16_PKT/M16_WT)에 대해 룰(R-A~R-D, SLA, SORT, MAXCAPA)을 평가해서:
- `stage` 0(없음)/1(조기경보)/2(주의보)/3(⭐확정)
- `unified_risk_score` 0~500, `unified_risk_level` 6등급
- 사건단위 CSV의 `lead_min`(사전 감지 분 — 클수록 좋음)

를 만든다. 판정은 전부 **정적 임계값**이다. 예: `M16HUB.QUE.TIME.AVGTOTALTIME1MIN >= 12.0분`.

### 1.2 관측된 실패 모드 (= "ML 실패가 너무 많다")

| 실패 모드 | 근거 (코드/문서에서 확인됨) | 결과 |
|---|---|---|
| **임계값 일반화 실패** | `04_임계값.md`에 "추천(2026-06)" vs "v4.1 원본" **두 벌**이 공존. M16HUB R-A 9.0→12.0, RB_fast 30→75, R-C 2→12 … 대부분 재조정됨 | 배포 후에도 계속 손으로 튜닝. 한 시점 임계가 다른 시점/부하에 안 맞음 |
| **반응 지연 (미탐/늦은 감지)** | 룰은 임계값을 **이미 넘은** 순간에만 발동. 트렌드/윈도우로 일부 보완하지만 본질은 사후 | `lead_min`이 짧음. 정체가 이미 시작된 뒤 잡힘 |
| **경보 요동 (오탐/알람 피로)** | 노이즈가 임계선 근처에서 튀면 stage가 켜졌다 꺼졌다. `RA_sus 지속비율`로 억제하지만 파라미터 민감 | 오경보 → 운영자 알람 피로 → 진짜 경보 무시 |
| **비대칭 위험 미반영** | 상단(폭주)과 하단 위험이 같은 임계 구조로 처리 | 위험한 tail을 놓치거나 과하게 반응 |

> 핵심 통찰: 이 시스템의 승부처는 **`lead_min`(얼마나 미리 잡나)**과 **오탐율**이다. 정적 임계값으로는 이 둘을 동시에 좋게 만들 수 없다 — 임계를 낮추면 오탐↑, 높이면 미탐↑. 그래서 "추천/원본" 임계 두 벌을 계속 저울질하는 것.

## 2. 왜 Chronos-Bolt인가

Chronos-Bolt는 사전학습된 시계열 예측 파운데이션 모델이다. **파인튜닝 없이(zero-shot)** 과거 context를 넣으면 미래 여러 스텝의 **분위수(q10~q90) 예측**을 한 번에 뽑는다.

이 문제에 잘 맞는 이유:
1. **선제 감지**: `AVGTOTALTIME1MIN`, 큐 카운트, STB 점유율 같은 신호를 **5~15분 앞서** 예측하면, 임계값을 넘기 *전에* 경보를 올릴 수 있다 → `lead_min`↑.
2. **확률(분위수) 출력**: 점 예측이 아니라 q10/q50/q90 구간을 준다 → "예측 구간의 상단(q90)이 임계를 넘을 확률"로 위험을 정량화 → 노이즈 한 방에 안 흔들림 → 오탐↓.
3. **수작업 튜닝 감소**: 임계값 두 벌을 저울질하는 대신, "예측된 신호가 임계를 넘을 확률"이라는 **하나의 일관된 척도**로 통합.
4. **엣지 배포 가능**: CPU에서도 구동(Apache-2.0). Jetson/온프렘 서버 모두 가능. 우리 수집기(매분 CSV)와 자연스럽게 붙음.

> 주의: Chronos-Bolt는 **예측 정확도**를 담당한다. 데드락 여부를 직접 판정하지 않는다. 판정은 다음 가드레일 레이어의 몫.

## 3. TightLoop Sentinel에 대한 솔직한 정리 (중요)

업로드하신 preprint의 *TightLoop Sentinel*은 **구현이 전부 비공개**다. 문서 원문:

> "Proprietary implementation details, internal state equations, parameterization, memory layout, and training or update mechanics are intentionally omitted."
> (tightloop_sentinel.md 하단에도: "세부 구현은 원문 확인 필요")

즉 **"뉴로모픽 신경망 엔진"이라는 이름의 블랙박스**이고, **가져다 쓸 코드가 없다.** 그래서 우리 계획은:

- ❌ TightLoop Sentinel 자체를 도입 — 불가능 (코드 없음)
- ✅ TightLoop이 하는 **"역할(forecast-to-action)"을 우리가 직접 구현** — 가능

논문이 공개한 "인터페이스 수준의 행동"은 그대로 재현 가능하고, 사실 우리 도메인엔 이게 더 낫다(우리 임계·룰 자산을 그대로 활용). 재현할 역할:
- **인과적 지연(causal-lag)**: 현재 잔차가 아니라 직전 신호로 조치 → 미래 정보 누수 없음
- **경계 있는(bounded) 조치**: 위험도/reserve를 정해진 범위로만 조정 (폭주 방지)
- **분포 인식**: 하단/상단 tail, center drift, regime 변화를 분리해 표현
- **비용 기반 평가**: undercoverage·shortfall·reserve waste·action churn 을 하나의 운영비용으로

## 4. TO-BE 아키텍처

```
매분 raw CSV (265 메트릭, 8영역)
        │
        ▼
[1] 신호 선택 & 히스토리 버퍼         ← 영역별 핵심 신호만 (예: M16HUB.QUE.TIME.AVGTOTALTIME1MIN)
        │   최근 context(예: 512분) 슬라이딩 윈도우
        ▼
[2] Chronos-Bolt 예측 (zero-shot)     ← 신호별로 미래 H분(예: 10분) q10/q50/q90
        │   출력: [영역·신호, 분위수, 예측지평]
        ▼
[3] Forecast-to-Action 가드레일       ← "TightLoop 역할" 우리 구현
        │   · 임계 초과 확률 P(예측구간이 임계>임계값) 계산
        │   · 경계 있는 위험도(0~500) — 기존 척도와 호환
        │   · 인과적/히스테리시스로 요동 억제 (켜짐/꺼짐 임계 분리)
        │   · 하단/상단 tail 비대칭 반영
        ▼
[4] stage / unified_risk_score / lead_min   ← 기존 predictor와 동일 출력 스키마
        │
        ▼
발동이벤트.csv + 사건단위.csv  (기존 소비자·LLM 해석기 그대로 재사용)
```

핵심 설계 원칙: **출력 스키마를 기존과 100% 호환**시킨다. 그래야 `05_결과해석.md`의 LLM 해석기, 대시보드, 사건단위 로직을 안 건드리고 예측 엔진만 교체/병행할 수 있다.

## 5. 통합 전략 — 교체가 아니라 "그림자 병행" 먼저

리스크를 줄이기 위해 3단계로 간다.

| 단계 | 방식 | 목적 |
|---|---|---|
| **A. Shadow (그림자)** | 룰베이스는 그대로 운영. Chronos 파이프라인을 **병렬로** 돌려 두 결과를 나란히 로깅 | 실서비스 영향 0으로, 예측이 실제로 더 미리/정확히 잡는지 검증 |
| **B. Hybrid (혼합)** | 룰 stage와 예측 stage를 결합(예: 둘 중 하나라도 확정이면 경보, 단 예측은 조기경보 lead 확보용) | `lead_min`은 예측으로 늘리고, 확정 판정 신뢰도는 룰로 유지 |
| **C. Forecast-first** | 예측+가드레일을 주 판정으로, 룰은 안전망/설명용 | 수작업 임계 튜닝 최소화 |

PoC는 **A(Shadow) 검증**까지가 목표. B/C는 A에서 지표가 좋게 나온 뒤 결정.

## 6. 평가 지표 (preprint의 운영지표 차용)

두 축으로 본다.

### 6.1 예측 품질 (신호 단위)
- **Coverage@80**: 실제값이 q10~q90 구간에 들어간 비율 (목표 ≈ 0.80)
- **정규화 잔차(mean/p90/p99)**, MASE/sMAPE (신호별)

### 6.2 운영 성과 (판정 단위 — 진짜 중요한 것)
- **lead_min ↑**: 사건을 몇 분 더 미리 잡나 (룰 대비 delta)
- **오탐율 ↓**: S3 확정 중 실제 정체가 아니었던 비율
- **미탐율 ↓**: 실제 정체 중 놓친 비율
- **action churn ↓**: stage가 무의미하게 켜졌다 꺼진 횟수 (알람 피로 대리지표)
- **operational_cost**: preprint 식 차용 —
  `under_weight·shortfall + reserve_weight·reserve_width + churn_weight·churn`
  (우리 도메인 비용으로 가중치 재정의)

> 성공 기준(예시, PoC 후 확정): Shadow에서 **lead_min +N분 & 오탐율 유지/감소**면 Hybrid 진행.

## 7. PoC 범위와 한계 (이번 세션)

**할 수 있는 것 (이 컨테이너):**
- 전체 파이프라인 **스캐폴드 코드** (신호선택 → 예측 → 가드레일 → 기존 스키마 출력)
- Chronos-Bolt 어댑터: 모델 로드/추론 래퍼 (+ 모델 없을 때 대체용 baseline 예측기)
- **합성 데이터 데모**: HUBROOM 정체 시나리오를 흉내낸 시계열로 파이프라인 end-to-end 동작 + 지표 리포트
- 기존 룰 결과 vs 예측 결과 **나란히 비교** 하네스

**이번 세션에 못 하는 것:**
- 실제 M16 raw CSV(사내 데이터)로의 검증 — 데이터가 이 컨테이너에 없음
- Chronos-Bolt 실 가중치 다운로드가 네트워크 정책에 막히면 real 추론 불가 → baseline 예측기로 파이프라인만 검증하고, 모델 로드는 사내/Jetson에서 붙이는 형태로 인계
- 성능 튜닝·프로덕션 배포
