# 카파시 — 리프터 HID 포화도(용량) 해석 원리 (왜 막히는가)

> 이 문서는 **계산이 아니라 "해석"** 을 위한 지식이다.
> 카파시 스크립트(`count_capacity.py`)가 뽑은 **포화도 데이터**를 받아서,
> "어디가 왜 막히는지 / 얼마나 심각한지" 를 사람이 이해하게 설명하는 데 쓴다.
> (SK하이닉스 M16A_BR OHT 반송)

---

## 1. 왜 포화도를 보는가 (목적)

HID 구역마다 **수용 가능한 차량 수의 한계(MAX_VHL)** 가 있다.
점유가 한계에 가까워지면 → 차량이 **들어가지 못하고 대기** → 리프터 진입·진출이 막히고 →
반송 지연, 심하면 **데드락**으로 번진다.

그래서 **"지금 몇 % 찼는가(포화도)"** 를 보면, 개수만으로는 안 보이는
**"막히기 직전인가 / 이미 막혔는가"** 를 판단할 수 있다.
(개수(근처차량수)는 일반 스킬, **한계 대비 비율**은 이 카파시 스킬의 영역)

---

## 2. 입력 데이터 (카파시 스크립트 결과 — 2개 파일)

**① 용량.csv (리프터별)**
`시각, Lifter, FAB, 근처HID, 경계mm, 점유차량수, 용량Max, 혼잡도%`

**② 용량_HID구역.csv (HID 구역별)**
`시각, HID, MAX_VHL, 주의_VHL, 점유차량수, 포화도%, 소속리프터`

| 컬럼 | 뜻 |
|------|----|
| 점유차량수 | 그 시점 그 HID 에 실제로 머무는 차량 수 (로그 HID_VALUE, 분당 peak) |
| MAX_VHL / 용량Max | 그 HID 의 최대 수용 한계 (Vehicle_Max) |
| **주의_VHL** | 시스템이 **차량 sweep(분산)을 시작하는 임계** (Vehicle_Precaution) |
| 포화도%/혼잡도% | 점유 ÷ MAX_VHL × 100 |
| 소속리프터 | 그 HID 를 근처로 두는 리프터들 (같은 HID 공유 리프터는 같은 값) |

---

## 3. 어떻게 해석하는가 (판단 규칙 — 이 문서의 핵심)

포화도를 읽고 **왜 그런지**를 다음 관점으로 설명한다.

- **포화도 높음 (대략 80% 이상)** = 그 HID 가 거의 꽉 참
  → 그 근처 리프터로 가는/오는 차량이 **대기·정체**. 유입이 처리량보다 많다는 신호.
- **점유 ≥ 주의_VHL (Vehicle_Precaution 도달)** = 시스템이 **sweep(차량 분산)을 시작하는 운영상 경고 수준**.
  실제 설비가 개입하기 시작하는 임계 — 단순 "붐빔"보다 한 단계 심각.
- **특정 1분만 포화 급등(스파이크)** = **순간 병목**. 잠깐 몰렸다 풀린 것.
- **여러 분 연속 고포화** = **만성·구조적 병목**. 우선 개선 대상.
- **포화도 낮음** = 여유. 흐름이 많아 보여도 포화가 낮으면 **빨리 빠지는 정상 통과**다.
- **(일반 스킬 결과와 같이 볼 때) 근처차량수는 많은데 포화도 낮음** = 흐름만 많고 잘 빠짐 — 병목 아님.
- **(같이 볼 때) 근처차량수 적은데 포화도 높음** = 들어간 차가 **빠져나가질 못함** — 하류 막힘/리프터 처리 지연 의심.
- **죽은 라인** (트래픽 계속 0) 은 해석 대상에서 제외.

---

## 4. 무엇을 보고하는가 (결과물)

데이터를 읽고 아래를 글로 정리한다.

1. **어디** — 포화도 상위 HID/리프터 (꽉 찬 곳), 주의_VHL 도달 여부
2. **언제** — peak 시간대, 순간 스파이크 난 분
3. **왜** — 순간 몰림 / 만성 병목 / 하류 막힘 중 무엇인지 (위 규칙으로 판단)
4. **영향·권장** — 반송 지연·데드락 위험도, 경로 조정·스케줄 개선·모니터링 제안

---

## 5. 주의

- 점유는 로그의 **HID_VALUE**(실측 점유) 기준이다. IN−OUT 직접 추적은 100% 초과 버그가 있어 쓰지 않는다.
- 같은 HID 를 공유하는 리프터들은 같은 포화도를 가진다 (HID 단위 집계).
- 숫자는 스크립트 결과 그대로 사용하고 임의로 수정하지 않는다. 데이터에 없는 시각/구역은 추측하지 않는다.
