# 3단계 데드락 룰베이스 사건 탐지 — 상세 가이드

> **목적**: M16HUB OHS(반송) 시스템에서 발생하는 3단계 데드락(정체)을 실시간으로 탐지·기록하는 룰베이스 시스템 설명
>
> **버전**: v4 (FABSTORAGERATIO 기반 R-D 룰 추가, 5/7 7시 SFA 정체 케이스 검증 완료)

---

## 1. 시스템 개요

**입력**: 1분 단위 CSV (Oracle `AWS_IDC_DATA_HIS` → SQL 추출 → 90~120분 슬라이딩)

**출력** (날짜별 자동 분리):
- `<YYYYMMDD>_발동이벤트.csv` — 매 분 1행, 단계별 상태
- `<YYYYMMDD>_사건단위.csv` — 진짜 위험한 S3 사건만 누적

**처리 흐름**:
```
SQL → CSV (1분 단위) → Python 룰엔진 → 매 분 평가 → S1/S2/S3 분류 → 사건 추적 FSM
```

## 2. 4가지 룰 정의

### R-A' (반송시간 룰)
**컬럼**: `M16HUB.QUE.TIME.AVGTOTALTIME1MIN` (1분 평균 반송시간, 분 단위)

| 룰 | 조건 | 의미 |
|---|---|---|
| **R-A' 절대** | 최근 10분 중 1MIN ≥ **9.0분**이 1회+ | 한순간이라도 반송이 길어졌다 |
| **R-A' 지속** | 최근 5분 중 1MIN ≥ **6.0분**이 3회+ | 비교적 길게(6분+) 지속됨 |

```python
TH_RA_VALUE = 9.0           # R-A' 절대 임계
TH_RA_SUSTAINED_VALUE = 6.0  # R-A' 지속 임계
TH_RA_SUSTAINED_COUNT = 3    # 5분창 3회+
```

### R-B (M14→M16 큐 누적 룰)
**컬럼**: `M16HUB.QUE.M14TOM16.MESCURRENTQCNT` (M14에서 M16HUB로 온 큐 수)

| 룰 | 조건 | 의미 |
|---|---|---|
| **R-B (느린 누적)** | 30분 전 대비 **+100 이상** | 큐가 꾸준히 쌓이는 데드락 |
| **R-B FAST (빠른 폭주)** | 10분 전 대비 **+30 이상** | 갑작스런 폭주 |

```python
TH_RB_DIFF_30 = 100   # 30분 +100
TH_RB_DIFF_10 = 30    # 10분 +30
```

### R-C' (리프터 역증가 룰)
**컬럼**: `M16HUB.LFT.6ABLxxxx.TOTAL_CURRENTQCNT` (10개 리프터 큐)

조건 (둘 다 만족):
1. **20분 전 대비 합 감소** (전체 큐는 줄어듦)
2. **개별 리프터 중 큐 증가 2개+** (특정 리프터에 큐 몰림 = 데드락 패턴)

```python
TH_RC_REVERSE = 2     # 역증가 리프터 2개+
```

**의미**: 시스템 전체적으론 큐가 처리되는데, 특정 리프터(들)에는 큐가 몰리는 비대칭 = 데드락 신호

### R-D (FAB 저장률 정체 룰) ★ NEW
**컬럼**: `M16HUB.STRATE.ALL.FABSTORAGERATIO` (FAB 내부 저장 사용률 %)

| 조건 | 임계 | 의미 |
|---|---|---|
| FABSTORAGERATIO ≥ **25.0%** | 정상 0~5%, 정체 24~32% | FAB 저장공간이 가득 차서 OHT가 받지 못함 |

```python
TH_RD_FABSTORAGE = 25.0
```

**검증 결과** (5/7 7시 SFA 정체):
- 정상: 0~5%
- 5/7 7시 정체 시작: 10.06% → 24.26% → 28.99% → **31.95%** (피크)
- 회복 후: 1~3%
- 5/8 정상시간: <1%

## 3. 단계(Stage) 정의

매 분 4가지 룰을 평가하여 단계 판정:

| 단계 | 조건 | 의미 | 사건단위 기록 |
|---|---|---|---|
| **0 (정상)** | 모든 룰 미충족 | 이벤트 없음 | ❌ |
| **S1 (조기경보)** | R-A' 2회+ OR R-A' 지속 | 반송시간 길어짐 | ❌ |
| **S2 (주의보)** | R-B OR R-B FAST | 큐 누적 시작 | ❌ |
| **S3 (확정)** | **R-A' AND R-C' AND (R-B OR R-D)** | **진짜 데드락** | ✅ |

**S3 룰 상세**:
```python
s3 = ra_trig AND rc_trig AND (rb_trig OR rd_trig)
```

즉:
- 반송시간 발동 ✓
- 리프터 비대칭 발동 ✓
- (M14→M16 큐 누적 ✓) **또는** (FAB 저장률 정체 ✓)

## 4. 사건 추적 FSM

3단계 발동이 시작되면 사건이 시작되고, 일정 시간 동안 재발동이 없으면 종료:

```
    [IDLE]
       │ S3 발동
       ▼
[IN_INCIDENT] ──── S3 재발동 (10분 이내) ───→ [IN_INCIDENT] (refire +1)
       │
       │ 10분간 S3 미발동
       ▼
    [IDLE]  → 사건 종료, 사건단위.csv 기록
```

**상수**:
```python
INCIDENT_END_GAP_MIN = 10        # 사건 간 간격 (10분 이상이면 별개 사건)
PREDICT_LOOKBACK_MIN = 60        # 사건 시작 전 60분 내 첫 S1/S2 시각 = predict_time
```

## 5. 발동이벤트 CSV 형식 (매 분 1행)

| 컬럼 | 설명 | 예시 |
|---|---|---|
| `file` | 입력 파일명 | `90min.csv` |
| `datetime` | 시각 | `2026-05-07 07:32` |
| `date` | 날짜 | `2026-05-07` |
| `time` | 시간 | `07:32` |
| `stage` | 단계 (0~3) | `3` |
| `stage_name` | 단계명 | `3단계 ⭐확정` |
| `prev_stage` | 이전 단계 | `2` |
| `transition` | 단계 전환 | `2→3` |
| `reason` | 발동 사유 | `R-D FAB저장률 정체 (FABSTORAGE=28.99%, 1MIN 8.55)` |
| `relation` | 룰 근거 (R-A'/R-B/R-C' 상세) | `[R-A' Y] AVGTOTALTIME1MIN=8.55분 (≥9분 10분창 0회, 지속Y) \| [R-B N] M14→M16 30분Δ=42 (≥100), 10분Δ=12 (≥30 fast) \| [R-C' Y] 역증가 6개 (≥2): LFT.6ABL...; trend=-15` |

**특징**:
- stage=0 (정상)일 때 → `stage_name=이벤트없음`, 나머지 빈칸
- 매 분의 **3룰 상태 모두 표기** → 어느 룰이 부족한지 즉시 진단 가능

## 6. 사건단위 CSV 형식 (S3 사건 1건당 1행)

| `contrib_breakdown` | 룰별 기여도 |
| `anomaly_explanation` | 사람이 읽을 수 있는 요약 |
| `early_warning` | 사전 인지 메시지 |
| `relation` | 사건 근거 컬럼 풀네임 (LFT 역증가 IDs 포함) |

## 9. 룰 임계값 조정 가이드

`3단계_룰베이스_사건단위.py` 상단 상수로 조정:

```python
# R-A' (반송시간)
TH_RA_VALUE = 9.0              # 절대 임계 (분) — 낮추면 민감, 올리면 보수적
TH_RA_SUSTAINED_VALUE = 6.0    # 지속 임계 (분)
TH_RA_SUSTAINED_COUNT = 3      # 5분창 N회+

# R-B (M14→M16)
TH_RB_DIFF_30 = 100   # 30분 +N
TH_RB_DIFF_10 = 30    # 10분 +N (FAST)

# R-C' (리프터)
TH_RC_REVERSE = 2     # 역증가 리프터 N개+

# R-D (FAB 저장률) ★
TH_RD_FABSTORAGE = 25.0   # 임계값 (%)
                          # 25 → 5/7 정체 잡음 (현재 권장)
                          # 30 → 5/7 정체 못 잡음 (너무 보수적)
                          # 20 → 위양성 증가

# 사건 추적
INCIDENT_END_GAP_MIN = 10        # 10분 이상 무발동 시 사건 종료
PREDICT_LOOKBACK_MIN = 60        # 사전 인지 추적 윈도우
```

## 11. SQL 수집 쿼리

`AWS_IDC_M16HUB_실시간_v4.sql`:

```sql
-- 윈도우 크기 (분)
DEFINE WINDOW_MIN = 90

-- SYSDATE 기준 과거 N분 ~ 현재
WHERE CRT_TM BETWEEN SYSDATE - &WINDOW_MIN/1440 AND SYSDATE
```

42개 컬럼 (기존 32 + M14B 진단 10) 출력. 1분마다 cron/scheduler로 호출.

## 12. 트러블슈팅

### Q: 5/7 정체가 안 잡혀요
A: 입력 CSV에 `FABSTORAGERATIO` 컬럼이 있고 데이터가 채워져 있는지 확인. 임계 25 미달이면 잡히지 않음.

### Q: 위양성이 너무 많아요
A: `TH_RD_FABSTORAGE`를 28~30으로 상향. 또는 5/6 9시처럼 R-A'+R-C'까지 같이 발동하는 시점은 진짜 정체일 가능성도 검토.

### Q: 같은 정체가 여러 사건으로 쪼개져요
A: `INCIDENT_END_GAP_MIN`을 30으로 늘림. 단, 4/21 검증 사건 2건이 1건으로 합쳐질 수 있으니 주의.

### Q: 새 컬럼 추가하고 싶어요
A: `iter_star_rows()`에 컬럼 읽기 추가, `evaluate_rules()`에 새 룰 정의, `s3` 식에 OR로 결합.
