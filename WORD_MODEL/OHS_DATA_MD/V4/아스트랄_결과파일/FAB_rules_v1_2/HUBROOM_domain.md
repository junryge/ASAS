# HUBROOM 운영 도메인 및 룰 설계·평가 원칙

기준일: 2026-09-23. 출처: 사용자 현장 설명. 원천데이터·메신저 분석 전 확정한 해석 기준이다. 사용자 현재 상태 설명을 과거 전체 기간의 상태로 소급하지 않는다.

## 1. 공간·장비 명칭

- HUBROOM, bridge, M14HUB, M16HUB는 같은 HUB 공간을 지칭한다.
- M16 3F(HUB)는 M14 측 층 표기로는 4F에 해당한다.
- 4AFC3201은 남측, 4AFC3301은 북측 CNV이다. 대화의 남/북 표현이 장비 ID와 충돌하면 장비 ID를 우선한다. 원문 방향명과 정규화 결과를 함께 보관한다.
- 점수는 M14A·M14B·M16A·M16B·M16HUB별 실제 반송 영향을 표현한다. 조치 담당 FAB과 영향받는 FAB은 다를 수 있다.

## 2. MAXCAPA 특례

| 구분 | 확정 설명 |
|---|---|
| 적용 장비·방향 | 6ABL 리프터의 3F AI, HUB→M16A 6F 방향 |
| 원천지표 | M16HUB.QUE.LFT.3F_LFT_MAXCAPA: 현재 수집하는 입구 MAXCAPA 집계값 |
| 예외 | 이 집계 MAXCAPA 합을 초과해도 반송 가능 |
| 별도 설정 | TOTALMAXCAPA 또는 ALTMAXCAPA, 현재 280이며 자주 바뀌지 않음 |
| 적용 범위 | 이 6ABL 3F AI 구간만. 다른 리프터·층·방향에 일반화하지 않음 |

### 해석 원칙

- 집계 MAXCAPA를 완전한 물리 용량 또는 절대 반송 상한으로 간주하지 않는다.
- 현재 물량/MAXCAPA가 1을 넘었다는 이유만으로 오류·포화·반송 불가를 확정하지 않는다. 반드시 같은 범위의 물량인지도 확인한다.
- 280을 기존 MAXCAPA에 더하거나 280/MAXCAPA 관계를 임의로 공식화하지 않는다. 포트별 조건·ALT 전환과의 정확한 적용 우선순위는 필요시 확인한다.
- 사용자 설명은 현재 설정이다. 8/11~9/15에도 계속 280이었는지는 기록이 없으면 미확정으로 둔다.
- MAXCAPA 감소는 작업자 제어 또는 장비 가용성 감소에 따른 조치일 수 있다. 변경 시각·변경 전후 값·변경 목적과 실제 반송 영향을 함께 본다. 조치 자체에 무조건 장애 점수를 주지 않는다.

## 3. 6FIOB MLUD와 MMDM

### 목적지 분산

M16A→M14 물량이 설정 기준을 초과하면 HOST(MES)가 반송 목적지를 6FIOB 계열로 내린다. 기준량은 작업자가 MMDM 시스템에서 수동 조정한다. 변경 멘트가 남을 수도 있지만 생략되는 경우도 많다.

- MMDM 기준은 물량 분산과 MLUD 유입량을 바꾸는 운영 조건이다.
- 변경 기록이 없다는 이유로 기준이 일정했다고 가정하지 않는다.
- MLUD 비중 급변이 장비 이상인지, 목적지 정책 변경인지 데이터만으로 완전히 구분하지 못할 수 있다. 근거가 없으면 원인 미확인으로 표시한다.

### 수동 반출 지연과 정체 가능 경로

1. HUB OHT가 FOUP을 6FIOB MLUD AI에 내려놓는다.
2. FOUP이 Manual OUT(MO)으로 이동한다.
3. 작업자가 MO의 FOUP을 손으로 제거하여 M14로 운반한다.
4. MO에서 제거가 지연되면 AI의 후속 FOUP이 이동하지 못하고 AI를 점유할 수 있다.
5. 다른 OHT의 DEPOSITED 실패(PIO) 및 정체가 발생할 수 있고 지속되면 데드락으로 이어질 수 있다.

이것은 가능한 인과 경로이며 모든 6FIOB 출고지연을 데드락으로 확정하지 않는다. PIO·MLUD향 적재 OHT·HUB 적재 OHT·내부 JOB·STB 저장률·반송시간을 대조한다. 완료 반송시간은 완료 CMD만 반영하므로 심한 정체 중 0이 되거나, 정체 해소 후 긴 CMD가 완료되면서 뒤늦게 튈 수도 있다.

## 4. 수동 반출 CNV 6ACNVB01

- 역할: 6FIO MLUD처럼 작업자가 FOUP을 회수하여 대차로 M14에 옮기는 반출 경로. HUB OHT 부하를 줄이기 위한 장치다.
- 연결: 6ABL6031·6ABL6032(현장 명칭 3호기)의 3F AO와 연결된다.
- 경로: 6ABL 6F AI 반입 → 리프터 3F AO → 직접 연결된 6ACNVB01 → 긴 컨베이어 이동 → MO → 작업자 수동 회수 및 M14 운반.
- 이 경로는 리프터 3F 출고 뒤 HUB OHT 반송을 거치지 않는다.
- 각 리프터 3F AO에는 CNV 연결 포트와 OHT가 집을 수 있는 포트가 있어 선택적으로 사용 가능하다.
- 사용자 설명상 현재는 두 호기 중 하나를 CNV 출고, 다른 하나를 OHT 출고로 운용하는 것으로 예상된다. 어느 호기가 어느 모드인지와 과거 기간별 모드는 아직 확정하지 않는다.
- 현재 6ACNVB01 관련 데이터는 수집하지 않는다.

### 점수 해석상 한계

- 6ABL6031/6032의 6F→3F 물량이 전부 HUB OHT 부하로 이어진다고 가정하지 않는다.
- 호기별 물량 불균형이 운용 모드 차이 때문일 수 있으므로 곧바로 고장으로 판단하지 않는다.
- 관측되지 않는 컨베이어 완료량·점유·MO 대기값을 0으로 채우거나 다른 지표로 확정 복원하지 않는다.
- 수동 반출 경로가 있어도 일반 자동 FAB 간 반송에 임의 우회가 없다는 기존 설명을 뒤집지 않는다. 지정된 수동 분산 운용과 자동 대체 경로를 구별한다.

## 6. 시간 분리와 평가

| 기간 | 역할 |
|---|---|
| 8/11~9/11 | 데이터 품질·평상시 분포 분석, 대화 근거 사건 정리, 후보 룰·임계치·지속 조건 설계 |
| 9/12~9/15 | 고정된 룰의 별도 평가. M14A 무언정지와 HUB 데드락 및 주변 구간 포함 |

- 9/2 M16B 전체 OHT 수분간 STOP 작업은 사용자 확인이 있는 반송 영향 사례로 우선 검토한다. 계획 작업과 비계획 장애를 별도 표시한다. 정지 의도와 실제 반송 영향은 서로 다른 평가 축이다.
- 평가 전에 입력·임계치·지속/해제·배점을 고정한다. 기준 분포·정규화 값도 설계 구간만으로 정한다.
- 평가는 시점 t까지의 자료만 사용하는 순방향 재생으로 수행한다. 미래 값·중앙 이동평균·사후 조치 정보를 실시간 입력으로 넣지 않는다.
- 평가 시작 시 필요한 과거 창은 설계 구간 말미 자료로 준비할 수 있다. 이는 미래 정보 사용과 다르다.
- 9/12~15 사례는 이미 대화에서 알려졌으므로 완전한 미공개 맹검이라고 주장하지 않는다. 결과를 보고 수정하면 개선 후 재평가로 구분하고 추가 기간 검증이 필요하다.
- 두 대표 장애를 맞추는지만 보지 않고 사건 탐지 여부·탐지 지연·대상 FAB 적합성·해제 지연·불필요 경보 지속도 함께 본다.

## 7. 메신저 기록의 정답 후보화

### 분류

| 종류 | 취급 |
|---|---|
| 실제 정체·지연·데드락 또는 반송 영향이 명시된 사건 | 영향 사건 후보. FAB·구간·시각과 근거 신뢰도 표기 |
| 9/2 M16B 전체 STOP 같은 계획 정지 | 계획 작업이지만 반송 영향 사례. 비계획 장애와 분리 평가 |
| 국소 STB 작업·RAIL CUT·AI CLOSE/OPEN | 조치/작업 사실로 기록. 장애 또는 무영향 정상으로 자동 확정하지 않음 |
| 장비 DOWN/CLOSE·MAXCAPA 변경 | 장비 범위·목적·기간·영향을 대조할 운영 사건 |
| 6FIOB 출고지연·MO 회수 지연 | MLUD 정체 후보. 후속 PIO/물량 변화와 대조 |
| 대화가 없는 구간 | 영향 미확인. 정상 정답으로 일괄 지정하지 않음 |

### 사건 기록 항목

사건 ID, 대화방, 원문 시각·근거, 추정 발생/복구 시각과 불확실 범위, 장비 ID, 영향 FAB, 조치 담당, 계획 여부, 증상, 조치, MAXCAPA 변경 전후, 실제 영향 여부, 근거 신뢰도, 시계열 정합성, 미확인 사항을 분리한다.

- 3개 방에서 같은 사건을 언급하면 사건은 하나로 묶고 근거 메시지는 보존한다.
- 메시지 시각을 실제 시작/복구 시각으로 바로 확정하지 않는다. AI Open만으로 전체 정체 해소를 확정하지 않는다.
- 먼저 대화에서 독립적인 사건 근거를 정리하고 이후 시계열을 대조한다. 룰이 감지한 구간을 그대로 장애 정답으로 삼지 않는다.
- 시계열 급변으로만 발견한 구간은 후보/미확인으로 남기고 대화나 현장 확인이 있어야 확정도를 높인다.
- 대화 부재 구간의 경보는 즉시 오경보로 계산하지 않는다. 검토 대상 경보로 따로 보고한다. 불완전한 사건 목록으로 전체 정확도·재현율·F1이 확정된 것처럼 보고하지 않는다.

## 8. 다음 입력과 질문 정책

제공 예정: 8/11~9/11 설계 원천, 9/12~15 평가 원천, 3개 대화방의 반송 영향 관련 대화, 앞서 추가 예정인 방향 지표 3개.

대화는 시간·장비 ID·방 이름과 사건 앞뒤 맥락이 남는 텍스트가 유용하다. 파일을 받는 것을 막는 추가 질문은 없다. 데이터 정합성에 실제 영향을 주는 경우에만 과거 TOTALMAXCAPA 설정, 6031/6032 모드, MMDM 변경 시각, 불명확한 사건 시작/종료를 확인한다. 알 수 없는 사항은 미확인으로 유지한다.

## 9. 이번 원천 확인과 OSS 운영 설명

- 8/11~9/11 원천 CSV 32개와 대화 TXT 5개를 수신했다. 9/12~15 원천은 아직 수신하지 않았다. 대화에는 해당 평가 기간도 들어 있어 별도 분리했다. 추가 방향 지표 3개 모두 원천에 존재한다.
- 8/21 재고 삭제 사고 복구 시 OHT 전체 정지가 있었으며 대화의 STOP 11:36:24, 이동 11:37:23, 복구 11:37:35를 사건 근거로 기록했다. 이는 사용자 전체 FAB 모두 정지라는 뜻으로 확대하지 않고 M14A 방의 해당 영역 사건으로 취급한다.
- OSS는 MCS 하위에서 OHT 주행 알고리즘을 관장한다. 사용자 설명상 OSS 작업에는 전체 OHT 정지가 수반되고 ON/OFF로 반송 로직·트렌드가 바뀔 수 있다. 작업 예정/실제 시행/단순 연결/기능 지시 ON·OFF는 대화 근거에 따라 구분하고 실제 시행시각이 없으면 확정하지 않는다.
- 제조팀 LINE은 외부 공유·대응 근거, HUBROOM 및 M14A 내부방은 내부 조치 근거로 구분한다. 원문 시각은 실제 장애 시작과 다를 수 있다.
- Sorter는 별도 감시 점수를 제공한다. Sorter 물량만으로 FAB 위험에 가점하지 않고 층간/PIO/반송 지연이 실제로 동반될 때 해당 반송 지표로 반영한다.


## 2026-09-28 확인 및 정정 — v1.1 우선 적용

이 절은 앞선 Storage 해석과 충돌할 때 우선한다.

- HUBROOM Storage는 평소 비워두는 임시 대기 공간이다. CNV/LFT 수용량 또는 MAXCAPA 제한 등으로 STB에 대기했다가, MCS가 1분마다 반송 가능 상태를 확인해 다시 보낸다. 1분 타이머는 동작 원리이며 대기 해소를 보장하지 않는다.
- M14A/B·M16A/B Storage는 통상 높은 점유율로 운영되며 현장 공간 부족이 잦다. HUB의 빈 공간 기준을 다른 FAB에 적용하지 않는다. 다른 FAB Storage 지표별 분모·방향·정상기준은 이번에 새로 검증하지 않아 신규 가점을 추가하지 않았다.
- M16HUB.STRATE.ALL.FABSTORAGERATIO: HUBROOM 저장률, Reserved 카운트 포함. 실제 저장량만 또는 운반 CMD 수와 같다고 해석하지 않는다.
- M16HUB.STRATE.STB.3F_STORAGE_UTIL: 빈 공간 비율로 관리. 예약 포함 저장률과 합이 항상 100은 아니므로 단순 변환·결측 대체 금지. 정확한 예약/사용불가 공간 포함 범위는 추가 확인 대상이다.
- M16HUB.QUE.STB.3F_TO_M16A_3F_STB_CMD: STB에 저장하기 위해 OHT가 FOUP을 운반 중인 CMD 수. 저장된 FOUP 수가 아니다. STB로 가는 모든 사유가 포함되므로 MAXCAPA 제한으로 단정하지 않는다.
