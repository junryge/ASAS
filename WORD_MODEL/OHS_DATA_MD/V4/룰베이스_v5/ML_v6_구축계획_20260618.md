# ML v6 구축 계획 — 메신저 정체 30분 사전 예측 (XGBoost 독립)

> 작성 2026-06-18 · 결정: 라벨=메신저 Episode / 독립 예측기(하이브리드 나중) / 30분 단일
> 목표: **운영자가 메신저에 정체를 보고하기 30분 전에 ML이 미리 예측**

---

## 0. 한 줄 정의

```
입력: 어느 시각 t 의 설비 데이터(과거~현재만)
출력: P(향후 30분 안에 운영자가 정체를 인지/보고할 확률)  [0~1]
정답: 메신저 Episode 시작시각 (운영자 실제 인지) — orphan·CAPA변경 제외
```

---

## 1. 왜 이 설계가 "최고"인가 (핵심 원칙 5)

| 원칙 | 내용 | 안 지키면 |
|---|---|---|
| ① **진짜 정답** | 룰 출력(S3) 아닌 **메신저(운영자 인지)** 를 라벨로 | ML이 룰을 흉내내는 순환 (의미 없음) |
| ② **누수 차단** | 피처는 **시각 t 까지 데이터만**, 라벨은 t+1~t+30 | 미래 정보 누수 → 가짜 고성능 |
| ③ **시간 분할** | Train(과거) → Val → Test(미래) 시간순 | 랜덤 분할 시 미래로 과거 예측 = 누수 |
| ④ **불균형 처리** | 양성 ~4% → XGBoost + scale_pos_weight | 정확도 96%인데 다 "정상" 찍는 쓸모없는 모델 |
| ⑤ **올바른 지표** | 정확도 X → **PR-AUC + 리드타임** | 불균형에서 정확도는 거짓말 |

## 3. 라벨 생성 (메신저 → 분 단위)

```python
# 각 분 t 에 대해
y[t] = 1  if  (메신저 Episode 시작시각이 (t, t+30분] 안에 존재)
       0  otherwise
# orphan='Y', fault_type='CAPA변경' 제외
```
- 양성 분(minute) ≈ 110건 × 30분 ≈ **3,300분 / 8만 = 4.1%** (불균형)
- 신규 스크립트: `ml/make_labels_messenger.py`

## 4. 피처 설계 (시각 t 까지만)

| 그룹 | 내용 | 개수(약) |
|---|---|---|
| 현재값 | 핵심 설비 메트릭 (반송시간/큐/저장율/OHT/SLA/Sorter/리프터) | 60~130 |
| 롤링 통계 | 최근 5/10/30/60분 mean·std·max·min | 240 |
| 변화량(delta) | 1분·5분·10분 차이 + 추세(기울기) | 120 |
| 가속도 | delta의 delta (급변 감지) | 40 |
| 시간 컨텍스트 | 시(0~23)·요일·교대조 | 5 |
| (선택) 룰 신호 | 발동이벤트의 영역별 area_score·flow_score | 30 |

→ 총 **~400~500 피처**. feature_importance 상위 컷으로 정리.

**누수 방지 철칙**:
- 모든 피처는 **t 시점 이전 데이터로만** 계산 (rolling은 과거만).
- 라벨이 메신저(독립)라서 룰 점수는 피처로 써도 됨. 단 **그 분의 미래값 절대 금지**.

**NaN 처리**: forward-fill (5분주기 결측), 시작은 0. 학습구간 제한으로 NULL 컬럼 자동 해결.

신규: `ml/feature_builder_v6.py` (기존 v41 기반 수정)

## 5. 시간 기반 분할 (누수 방지)

| 구간 | 기간 | 용도 |
|---|---|---|
| **Train** | 2026-04-01 ~ 05-14 (44일, ~78%) | 학습 (내부 TimeSeriesSplit 5-fold) |
| **Validation** | 2026-05-15 ~ 05-20 (6일, ~11%) | 임계·하이퍼파라미터 튜닝 |
| **Test** | 2026-05-21 ~ 05-26 (6일, ~11%) | 최종 holdout (한 번만) |

> 랜덤 분할 절대 금지 — 반드시 시간순.

---

## 6. 모델 — XGBoost (이유: 라벨 적고 불균형)

```
XGBoost binary:logistic
  n_estimators 300~500, max_depth 4~5, learning_rate 0.05
  scale_pos_weight ≈ 음성/양성 비율 (~23)
  early_stopping (validation logloss)
  TimeSeriesSplit 5-fold (하이퍼파라미터 탐색)
```
- 딥러닝(LSTM) 안 씀: 라벨 110건엔 과적합. 데이터 더 쌓이면 후순위.
- (옵션) LightGBM 병행 비교 — 더 빠르고 비슷.
- SHAP 으로 "왜 위험한지" 설명 → 운영자 신뢰.

신규/수정: `ml/train_xgboost_v6.py` (라벨 소스만 교체)

## 7. 평가 (정확도 금지, 이걸로 판단)

| 지표 | 의미 | 목표 |
|---|---|---|
| **PR-AUC** (test) | 불균형 대응 핵심 지표 | ≥ 0.4 |
| **리드타임** | ML score 임계 돌파가 메신저보다 몇 분 먼저 | 평균 ≥ 25분 |
| **사건 탐지율** | 메신저 110건 중 30분 전 잡은 비율 | ≥ 60% |
| **위양성률** | (단, 메신저 불완전 정답 감안 — 조용한 정체일 수 있음) | 참고용 |
| **vs 룰베이스** | 같은 test 구간에서 룰 대비 더 일찍/정확? | 비교표 |

신규: `ml/evaluate_v6.py` + 룰 vs ML 리드타임 비교

> ⚠️ **메신저는 불완전 정답** (운영자가 채팅 안 한 정체 존재). FP가 다 틀린 게 아님 — 룰베이스 검증 때 배운 교훈 그대로 적용.

## 8. 실시간 추론 (독립 — 하이브리드 X)

```
매분 → feature_builder_v6 (과거 윈도우) → XGBoost → ml_score_30m (0~1)
     → ml_predict/YYYYMMDD_predictions.csv 출력
     → (선택) Logpresso 별도 테이블 적재
```
- 룰베이스와 **병행만**, 융합 X (사용자 결정: 하이브리드 나중).
- 출력: `datetime, ml_score_30m, ml_level` (4단계: 안전<0.3 / 관심 / 경계 / 위험≥0.7)

신규: `ml/ml_runner_v6.py`
