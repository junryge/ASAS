# 주제 1. 룰베이스 고도화 (`hubroom_predictor.py`)

## 1-1. 왜 했나 (배경/문제)

기존 룰베이스는 8개 영역 메트릭으로 위험 점수를 냈지만 **운영에 쓰기 어려운 문제**가 있었다.

| 기존 문제 | 내용 |
|---|---|
| **알람 홍수** | 점수가 잠깐 떨어졌다 다시 오르면 **하나의 정체를 여러 사건으로 쪼갬** → 오탐 폭증 |
| **등급 혼란** | 점수→등급 매핑이 뒤죽박죽 (경계가 주의보다 낮은 점수) |
| **노이즈 사건** | 약한 신호(점수 낮음)도 사건으로 기록 → 운영자 피로 |
| **막연한 알람** | "어디서 무슨 정체인지" 라벨 없음 |
| **상태 불명** | 사건이 방금 떴는지, 오래됐는지 알 수 없음 |

→ "정확한 사건만, 명확한 등급으로, 무슨 정체인지까지" 보여주는 **v6 로 고도화**.

## 1-2. 무엇을 이용했나 (입력 데이터)

- **입력**: `M16A_HUBROOM_PR.csv` (설비 센서 데이터, 매분 수집)
- **8개 영역**: M16HUB / M14 / M14B / M16A / M16B / M16 / M16_PKT / M16_WT
- **9개 룰**: R-A(반송시간) / R-A_sus(지속) / R-B(큐누적) / R-B_fast(큐급증) / R-C(리프터역증가) / R-D(저장·OHT) / SLA / Sorter / MAXCAPA
- **정답 검증용**: 운영로그 파서 V2 가 만든 메신저 Episode (주제 2)

## 1-3. 어떻게 만들었나 (v6 핵심 개선 5가지)

| # | 개선 | 어떻게 |
|---|---|---|
| ① | **사건 진동 흡수** | 사건 종료 판정 간격(gap)을 10분 → **60분**. 점수가 잠깐 떨어졌다 60분 내 다시 오르면 **같은 사건** 으로 묶음 (재발 횟수만 +1) |
| ② | **5단계 등급 재정의** | 🔵관심 100 / 🟡주의 120 / 🟠경계 130 / 🔴위험 160 / ⚫발동 220 (한국 경보 체계 순서) |
| ③ | **노이즈 차단** | 사건 최고점수 **100 미만은 사건단위.csv 기록 X** (발동이벤트에서 모니터링만) |
| ④ | **장애유형 자동 라벨** | hot_area + 증상 조합 → `HUB-FAB정체`, `HUB-리프터역증가`, `M14-Sorter대기` 등 자동 부여 |
| ⑤ | **지속성·재발생 컬럼** | `지속 N분`(continuity_min), `재발 N회`(refire_count) 추가 → 운영자가 사건의 "나이" 즉시 파악 |

## 1-4. 무엇이 바뀌었나 (Before → After)

### 검증 진화 (4~5월 실데이터)

| 단계 | 정밀도 | 재현율 | 사전예측 | 평가 |
|---|---|---|---|---|
| 기존 (v4.1) | 21% | 44% | -1분 (늦음) | 시작점 |
| + 정답지 정정 | 15% | 44% | +2분 | 메신저 정답 정정 |
| + 임계 조정 | 15% | 36% | +1분 | ❌ 효과 없음 |
| **★ v6 (현재)** | **52%** | 14% | **+32분** | ✅ **돌파** |

> **핵심 깨달음**: 문제는 임계값이 아니라 **사건 연속성(진동)** 이었다. gap 60분으로 진동을 흡수하니 정밀도가 5배(15→52%), 사전예측이 음수→양수(+32분)로 전환.

### v6 등급별 성능 (현재)

| 등급 | 점수 | 정밀도 | 평균 사전예측 |
|---|---|---|---|
| 🔵 관심 | 100~119 | 41% | +17분 |
| 🟡 주의 | 120~129 | 67% | +18분 |
| 🟠 경계 | 130~159 | 60% | +45분 |
| 🔴 **위험** | **160~219** | **75%** | **+64분** |

> **성과**: 위험 등급(160+)은 **정밀도 75%**(4번 중 3번 진짜), 메신저 등록보다 **평균 1시간 먼저** 감지. 하루 0.5건으로 알람 피로도 낮음.

# 주제 2. 운영로그 파서 V2 (`운영로그_파서_v2.py`)

## 2-1. 왜 했나 (배경/문제)

룰베이스가 "잘 맞췄는지" 채점하려면 **"실제로 무슨 장애가 언제 났는지" 정답지**가 필요하다. 그 정답은 **운영자 메신저 채팅**에 있지만 사람 말이라 그대로 못 쓴다.

| 기존 문제 (v1) | 내용 |
|---|---|
| **거품(과대 카운트)** | 장애 1건에 운영자가 여러 번 채팅 → 메시지 1건=장애 1건 으로 세서 **152건으로 부풀려짐** |
| **유형 없음** | 무슨 종류 장애인지 분류 X |
| **복구/조치 혼재** | "조치 완료" 같은 복구 메시지도 장애로 카운트 |

→ 채팅을 **장애 단위(Episode)로 묶어** 정확한 정답지를 만드는 **V2**.

## 2-2. 무엇을 이용했나 (입력)

- **입력**: 운영자 메신저 로그 (`MA202605.txt` 등, 작성자·시각·본문)
- **출력**: `episode.csv` (장애 1건 = 1행) = 룰베이스 채점용 정답지

## 2-3. 어떻게 만들었나 (8단계 처리)

```
운영자 채팅: "Deadlock 으로 OHT 정체중입니다"
        ↓ 운영로그 파서 V2
Episode: 발생 18:34 / 유형 정체·병목 / 장비 OHT
```

| 단계 | 처리 |
|---|---|
| 1. 메시지 분리 | 채팅 로그를 작성자/시각/본문 단위로 |
| 2. 전처리 | 멘션·URL·이미지 제거 |
| 3. **카테고리 6종** | fault / action / recovery / rollback / cancel / normal |
| 4. **장애유형 7종** | 정체·병목 / 브릿지 / 리프터 / CNV / MLUD / 통신·에러 / 기타 |
| 5. 장비/라인 추출 | 정규식으로 장비명(4ABLD131, ZT, OHT 등) |
| 6. **Episode 묶기** | 같은 장비 + 30분 윈도우 = 1개 장애로 (거품 제거 핵심) |
| 7. Episode 라벨링 | 시작/종료/지속/심각도 |
| 8. 출력 | episode.csv (정답지) |

**제외 처리**: `orphan`(선행 fault 없는 복구), `CAPA변경`(운영자 조치이지 장애 아님)

## 2-4. 무엇이 바뀌었나 (Before → After)

### 거품 제거 효과 (5월 실측)

| 항목 | v1 (메시지 단위) | v2 (Episode 단위) |
|---|---|---|
| 장애 카운트 | **152건** (부풀려짐) | **107건** (정확) |
| 거품 제거 | — | **47% 감소** |
| 장애 유형 | 없음 | **7종 분류** |
| 복구/조치 처리 | 혼재 | **분리** |

### 실제 사례 (5/25)

```
메신저 원본 62건 메시지
   ↓ 파서 V2
실제 장애 4건 (orphan 6건·CAPA변경 10건 제외 후)
```

> **효과**: 과대 카운트를 제거해 **룰베이스 성능을 정확히 측정** 가능해짐. 이 정답지가 있어야 주제 1의 "정밀도 75%" 같은 수치를 신뢰할 수 있다.

# 종합 — 두 작업의 관계

```
[운영로그 파서 V2]  →  정답지(Episode)  ┐
                                        ├→  매칭/채점  →  "룰베이스가 30~60분 먼저 맞췄나"
[룰베이스 v6]       →  예측 사건         ┘
```

| 작업 | 역할 | 핵심 성과 |
|---|---|---|
| **룰베이스 고도화** | 정체 **예측** | 위험 등급 정밀도 75%, 평균 +32분 사전예측 |
| **운영로그 파서 V2** | **정답지** 생성 | 거품 47% 제거, 정확한 채점 기반 마련 |

> **두 작업이 합쳐져** 메신저 등록보다 **평균 30~60분 빠른 예측**을 신뢰성 있게 검증.
