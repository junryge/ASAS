# 📊 장표 1. 룰베이스 고도화 — Star 데이터 + LLM 자동 생성

## 1-1. 데이터 출처 (What Data)

반도체 **Fab(공장)** 환경에서 수집된 **Star 데이터** 를 기반으로 한다.

| 항목 | 값 |
|---|---|
| **데이터 종류** | Fab Star 데이터 (반송·저장·설비 상태 메트릭) |
| **전체 컬럼 수** | **255개** (수집 가능 전체) |
| **수집 단위** | 매분 (1분 1행) |
| **취합 출처** | 각 Fab(M14 / M14B / M16A / M16B / M16HUB 등) **실질 운영 데이터**를 통합 |
| **입력 파일** | `M16A_HUBROOM_PR.csv` |

> **Star 데이터** = Fab 내 다양한 설비·라인의 실시간 상태값(반송시간, 큐 카운트, 저장율, OHT 가동률 등)을 한 곳에 모아놓은 데이터셋. 룰베이스는 이 중 **각 팹의 핵심 운영 지표**를 선별해서 사용.

## 1-2. 룰베이스 고도화 핵심 — LLM 활용 자동 규칙 생성

기존 방식은 **사람이 직접 임계·조건을 정의** → 케이스 누락·튜닝 비용 큼.

**v6 부터는 LLM 을 활용해 규칙을 자동 생성** → 영역·시나리오별로 빠르게 확장 가능.

```
[Star 데이터 255 컬럼]
        ↓ 선별 + 패턴 학습
[LLM 으로 규칙 자동 생성]
        ↓
[8영역 × 9룰 = 룰베이스 v6]
```

## 1-3. LLM 이 생성한 규칙 샘플 (발췌)

| 규칙 ID | 조건 (LLM 자동 생성) | 의미 |
|---|---|---|
| **R-A**  반송시간 임계 | `AVGTOTALTIME1MIN ≥ 9.0분`  *(M16HUB 기준)* | 반송이 1분 평균 9분 넘게 걸리면 정체 시작 |
| **R-B**  큐 누적 | `6F_TO_HUB_JOB +84 / 30분`  *(M16A 기준)* | 30분새 작업 84건 이상 쌓이면 처리 지연 |
| **R-C**  리프터 역증가 | `리프터 큐가 ≥ 4대에서 거꾸로 증가` | 리프터가 막혀 짐을 못 빼는 상황 |
| **R-D**  저장 정체 | `STB.3F_STORAGE_UTIL ≥ 99.3%` | 저장 창고 가득 = 짐 받을 곳 없음 |
| **SLA**  4분 초과 | `TRANSPORT4MINOVERRATIO ≥ 14.05%` *(M16A)* | 4분 넘게 못 옮긴 짐 비율 = 체감 정체 |
| **흐름** 급변 | `M16A_2F_TO_HUB ≥ 평균의 3.0배` | 특정 경로 큐가 평소의 3배 → 급격한 부하 |

> **장점**: 새 시나리오·신규 영역 추가 시 LLM 이 패턴을 학습해 규칙을 제안 → 사람이 검토·승인만 하면 됨. 인력 의존도 ↓, 확장성 ↑.

# 📊 장표 2. 큐브 파서(Cube Parser) — 정답지 자동 생성

## 2-1. 입력 — 큐브 메시지 통째로 투입

운영자가 큐브(메신저)에 남긴 **시간대별 메시지 전체**를 한 번에 투입.

```
[입력 예시]
구간:  2026-05-25  01:00 ~ 05:00
메시지: "안녕하세요 6AFS6201 IN 늘고 있는데요 ERROR있나요?"
        "STK 이상 없습니다."
        "M16A ZT Max Capa 50%변경 부탁드립니다."
        "변경했습니다."
        "Deadlock 으로 인해 OHT 정체중입니다."
        ... (구간 내 수십~수백 건)
```

## 2-2. 기존 방식의 한계

| 방식 | 처리 단위 | 결과 |
|---|---|---|
| **과거 (v1)** | 메시지 1건 = 장애 1건 | 같은 장애에 운영자가 여러 번 채팅 → **장애가 152건으로 부풀려짐** |
| **문제** | 장애 건수가 많아질수록 같은 장애가 N번 카운트되어 **정답이 왜곡** | 룰베이스 채점이 부정확 |

## 2-3. 개선 — LLM 큐브 파서

LLM 이 메시지 흐름을 읽고 **같은 장애의 채팅들을 자동으로 묶어 "에피소드(Episode)" 단위**로 변환.

```
[원본 메시지 흐름]                          [LLM 파서 처리]
01:14  "OHT 정체중"        (fault)      ┐
01:20  "조치중입니다"      (action)     ├──→  Episode 1
01:35  "M16A ZT Capa 50%"  (action)     │     · 시작: 01:14
01:48  "변경 완료"         (recovery)   ┘     · 유형: 정체·병목
                                              · 장비: OHT
                                              · 지속: 34분

03:02  "Lifter 4ABLD131"   (fault)      ┐
03:18  "복구 완료"         (recovery)   ┘──→  Episode 2 (리프터)
```

**처리 단계 요약**:
1. 메시지 카테고리 분류 (fault / action / recovery / rollback / cancel / normal)
2. 장애 유형 인식 (정체·병목 / 브릿지 / 리프터 / CNV / MLUD / 통신 / 기타)
3. 같은 장비·시간 윈도우(30분) 묶기
4. orphan(선행 fault 없는 복구), CAPA변경(운영자 조치) 제외

## 2-4. 최종 목적 — 룰베이스와의 시너지 (핵심)

큐브 파서가 만든 에피소드는 **그 시각의 Star 데이터와 매칭**되어 **"정답"** 이 된다.
이 정답지를 **룰베이스(장표 1)에 피드백** 해서 더 정교하게 고도화.

```
┌────────────────────────────────────────────────────────────┐
│                                                            │
│   [큐브 메시지]  →  LLM 큐브 파서  →  Episode (정답)        │
│                                          │                  │
│                                          ▼                  │
│                            ┌─────────────────────┐          │
│                            │  그 시각의 Star 데이터  │         │
│                            │  (정답 = 실제 장애일 때 │          │
│                            │   메트릭은 이랬다)      │         │
│                            └──────────┬──────────┘          │
│                                       ▼                     │
│                            [LLM 룰베이스 (장표 1)]            │
│                            "정답 패턴" 학습/검증              │
│                            → 규칙 정교화 / 새 규칙 자동 생성    │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

### 시너지 효과

| 항목 | 단독 사용 시 | 큐브 파서 + 룰베이스 결합 |
|---|---|---|
| 룰베이스 정확도 검증 | 불가 (정답이 없음) | **가능** (Episode = 정답지) |
| 새 규칙 발굴 | 사람이 케이스 발굴 | **LLM 이 정답지 패턴 분석해 자동 제안** |
| 거짓 알람 식별 | 어려움 | 정답에 없는 알람 = 오탐 후보로 즉시 식별 |
| 누락 사건 발견 | 어려움 | 정답에는 있는데 룰이 못 잡은 사건 = 신규 규칙 필요 신호 |

# 🎯 두 작업의 인과관계 (전체 그림)

```
   [Fab Star 데이터 255 컬럼]              [큐브 메시지]
            │                                    │
            ▼                                    ▼
   [LLM 룰베이스 v6]  ◄────── 정답 피드백 ─────  [LLM 큐브 파서]
   8영역 × 9룰 자동 생성                   Episode(정답지) 자동 묶음
            │                                    │
            └───────────────┬────────────────────┘
                            ▼
              정체 사전 예측 (메신저 등록보다 30~60분 먼저)
```

## 종합

| 작업 | 역할 | LLM 활용 포인트 |
|---|---|---|
| **룰베이스 고도화** | Fab Star 데이터로 정체 **예측** | 규칙 자동 생성 |
| **큐브 파서** | 메시지로 **정답지** 생성 | 같은 장애 메시지 자동 묶기 |
| **결합** | 정답지 → 룰베이스 검증·재고도화 | 정확도 지속 개선 사이클 |

> 두 작업은 **각각이 아니라 결합돼야 가치**가 나옴. 큐브 파서가 정답을 만들고, 그 정답으로 룰베이스가 진화하는 **지속 개선 루프**.
