# 룰베이스 성능 평가 기준 명세서

> 본 명세서는 룰베이스 v6 의 성능 평가에 사용된 **모든 판단 기준 (윈도우, 매칭 룰, 리드타임 정의)** 을 정리한 것입니다. 고객사 자체 검증 시 동일 기준 적용 권장.

| 데이터 | 파일 | 단위 |

## 2. "실제 장애" 정의 (정답지)

운영로그_파서_v2.py 가 메신저 로그를 Episode 단위로 묶은 결과를 정답지로 사용.

### 2.1 Episode 카운트에서 **제외** 하는 케이스
| 케이스 | 이유 |
|---|---|
| `is_orphan = Y` (선행 fault 없는 복구 메시지) | 장애 발생 메시지 없음 → 정답지 불완전 |
| `fault_type = CAPA변경` | 운영자의 운영 조치이지 시스템 장애 아님 |

### 2.2 평가 대상 Episode 7종 유형
정체/병목 · 브릿지 · 리프터 · CNV · MLUD · 통신/에러 · 기타

## 3. 룰베이스 "사건" 정의

발동이벤트.csv 의 매분 데이터에서 S3 (확정) 조건이 만족된 연속 구간을 사건으로 묶음.

### 3.1 S3 (확정) 조건
```
S3 = any_RA AND (any_RD OR any_SLA OR any_RC) AND (any_RB OR flow_severe)
```
- **any_RA**: 5개 영역(M16HUB/M14/M14B/M16A/M16B) 중 1개 이상 반송시간 임계 초과
- **any_RD**: M16HUB FAB저장 ≥ 25.75% 또는 STB저장 ≥ 99.3%
- **any_SLA**: 영역별 SLA 임계 초과 1개 이상
- **any_RC**: M16HUB 리프터 역증가 ≥ 4 + 감소 트렌드
- **any_RB**: 30분 큐 누적 임계 초과 1개 이상
- **flow_severe**: flow_score ≥ 15

### 3.2 사건 묶기 (진동 흡수)
```
INCIDENT_END_GAP_MIN = 60분
```
S3 조건이 잠깐 깨졌다 60분 안에 다시 만족되면 **같은 사건**으로 묶음 (refire_count++).
60분 넘게 끊기면 종료 → 다음 만족 시 **새 사건**.

### 3.3 사건 기록 임계
```
점수 < 100 → 사건단위.csv 기록 X (노이즈)
점수 ≥ 100 → 5단계 등급 부여:
  관심 100~119 / 주의 120~129 / 경계 130~159 / 위험 160~219 / 발동 220+
```

## 4. 매칭 규칙 — "예측했다 / 못했다" 판단

### 4.1 매칭 윈도우
사건의 시간 구간을 다음과 같이 정의:
```
사건 구간 = [predict_time - 30분, end_time + 60분]
```
- **PRE (30분)**: 룰베이스 예측 30분 전부터 매칭 허용
- **POST (60분)**: 사건 종료 후 60분까지 매칭 허용 (복구 지연 고려)

### 4.2 매칭 조건
메신저 Episode 의 `start_time` (운영자 인지 시각) 이 사건 구간 안에 들어오면 **매칭 (TP)**.

### 4.3 매칭 한도
```
MAX_LEAD_MIN = 120분
```
룰베이스가 메신저보다 **120분 이상 일찍** 떴으면 **다른 사건으로 간주** (매칭 제외).
→ 6시간 전 알람이 6시간 후 장애를 흡수하는 과장 방지

### 4.4 1:1 최근접 매칭
- 한 사건은 한 Episode 만 매칭 가능 (이미 matched 면 스킵)
- 한 Episode 는 시간이 **가장 가까운** 미사용 사건과 매칭
- → 4시간 전 사건이 흡수하는 과장 방지

---

## 5. 리드타임 계산 — "몇 분 전에 감지했나"

```
리드타임 = 메신저 발생시각 (Episode.start_time) - 룰베이스 예측시각 (사건.predict_time)
```

| 부호 | 의미 |
|---|---|
| **+ 양수** | 룰베이스가 메신저보다 먼저 감지 (사전 예측 성공) |
| **0 또는 - 음수** | 룰베이스가 메신저와 동시 또는 늦음 |

### 5.1 사전 예측 성공 판정
- 리드타임 > 0 → "사전 예측 ✅"
- 리드타임 ≤ 0 → "동시 또는 사후 감지"

### 5.2 리드타임 통계 지표
- **평균 리드타임**: 전체 매칭 사건 리드타임 평균
- **사전 예측률**: (리드타임 > 0 사건수) / 전체 매칭 사건수
- **최대 리드타임**: 가장 일찍 감지한 사건의 리드타임

## 6. TP / FP / Miss 정의

| 분류 | 정의 | 의미 |
|---|---|---|
| **TP (정탐)** | 룰베이스 사건 ∩ 매칭 성공 Episode | 알람 울렸고 진짜 장애 있음 |
| **FP (오탐)** | 룰베이스 사건 ∩ 매칭 실패 | 알람 울렸으나 메신저에 장애 없음 |
| **Miss (놓침)** | Episode ∩ 매칭 실패 (룰베이스가 못 잡음) | 진짜 장애였는데 알람 안 울림 |

### 6.1 정밀도 / 재현율
```
정밀도 (Precision) = TP / (TP + FP)
재현율 (Recall)    = TP / (TP + Miss)
```

### 6.2 FP 해석 주의사항
**FP 가 모두 "헛알람"이 아님:**
- 메신저는 운영자가 "채팅으로 보고한 장애" 만 기록 → 운영자 미인지 정체는 정답지에 없음
- 룰베이스가 잡은 점수 100+ 사건이 메신저에 없다 = 진짜 헛알람일 수도, 운영자가 못 본 진짜 정체일 수도
- → **실제 정밀도는 측정치보다 높을 가능성**

## 7. 평가 절차 (재현 가능)

### Step 1: 룰베이스 사건 생성
```bash
python hubroom_predictor.py <raw_data.csv> -o ./predict_tobe
```
→ `YYYYMMDD_사건단위.csv` + `YYYYMMDD_발동이벤트.csv` 생성

### Step 2: 메신저 Episode 생성
```bash
python 운영로그_파서_v2.py <messenger.txt> --out ./episode_out
```
→ `YYYYMMDD_HHMMSS_episode.csv` 생성

### Step 3: 매칭 + 평가
```bash
python 사건_예측검증.py "predict_tobe/*_사건단위.csv" "episode_out/*_episode.csv"
```
→ 콘솔 출력: TP/FP/Miss, 정밀도/재현율, 평균 리드타임

### Step 4 (선택): 종합 검증 — 모든 기준 반영
```bash
python 종합검증_v6.py
```
→ 등급별 분석 + 진동 분석 + 베스트 사례 출력

## 8. 등급별 평가 (v6 기준)

| 등급 | 점수 | 알람 의미 |
|---|---|---|
| 🔵 관심 | 100~119 | 약한 신호 — 참고용 |
| 🟡 주의 | 120~129 | 모니터링 시작 |
| 🟠 경계 | 130~159 | 원인 확인 시작 |
| 🔴 위험 | 160~219 | 즉시 조치 준비 (정밀도 75%) |
| ⚫ 발동 | 220+ | 즉시 개입 |

**운영 적용 시 권고:** 위험 등급(160+) 부터 즉시 알람. 그 미만은 대시보드 모니터링.

| 항목 | 기준 |

| 정답지 | 운영로그_파서_v2 Episode (orphan + CAPA변경 제외) |

## 10. 논의 필요 사항 (고객 검토 요청)

1. **매칭 윈도우 [predict-30, end+60]** 가 적절한가?
   - 일부 장애는 종료 후 90분~120분 후 메신저에 등록될 수도 있음
   - POST 60분 → 90분 검토 가능

2. **MAX_LEAD 120분** 이 적절한가?
   - 일부 시스템은 사전 신호가 3~4시간 전에 떠도 같은 사건일 수 있음
   - 도메인 검토 후 조정 가능

3. **CAPA변경 제외** 가 적절한가?
   - 운영자 조치라 장애 아님으로 처리했으나, CAPA 자체가 장애 대응이라면 카운트해야 한다는 의견도 가능

4. **사건 묶기 gap 60분** 이 적절한가?
   - 진동 흡수 위해 도입했으나, 실제로 별개 사건을 합쳐버릴 위험도 있음

5. **점수 100 임계** 가 적절한가?
   - 노이즈 차단 위해 도입했으나, 작은 사건 (관심 등급) 도 보고 싶다면 조정 가능
