# 📊 장표 1. 룰베이스 고도화 — Star 데이터 + LLM 자동 규칙

## 1-1. 데이터 출처 (What Data)

| 항목 | 값 |
|---|---|
| 데이터 종류 | 반도체 **Fab Star 데이터** (반송·저장·설비 상태) |
| 전체 컬럼 | **약 255~266개** (수집 전체) |
| 수집 단위 | 매분 1행 |
| 취합 출처 | 각 Fab(M14/M14B/M16A/M16B/M16HUB 등) 실운영 데이터 통합 |
| 입력 파일 | `M16A_HUBROOM_PR.csv` |

## 1-2. 무엇을 보나 — 8개 영역 × 9개 룰

**8개 영역(Area)** = Fab 내 반송 구역. 각 구역의 상태를 따로 평가.

| 영역 | 무슨 구역 |
|---|---|
| **M16HUB** | M16 허브룸 (반송 중심·저장) |
| **M14 / M14B** | M14 / M14B 라인 |
| **M16A / M16B** | M16A / M16B 라인 |
| **M16 / M16_PKT / M16_WT** | M16 본체 / 포켓 / 대기 |

**9개 룰(Rule)** = 각 영역에서 정체를 감지하는 조건.

| 룰 | 무엇을 감지 | 사용 컬럼 | 임계(예) |
|---|---|---|---|
| **R-A** 반송시간 | 짐 이동이 느려짐 | `QUE.TIME.AVGTOTALTIME1MIN` | ≥ 9.0분 |
| **R-A_sus** 지속 | 반송 지연이 계속됨 | (R-A 가 여러 분 연속) | — |
| **R-B** 큐누적 | 대기 작업이 쌓임 | `QUE.ALL.{n}F_TO_HUB_JOB` | +84/30분 |
| **R-B_fast** 큐급증 | 큐가 급격히 증가 | (10분 변화량) | — |
| **R-C** 리프터역증가 | 리프터가 막혀 큐 역증가 | `LFT.6ABLxxxx` (리프터 10대) | ≥ 4대 |
| **R-D** 저장정체 | 창고 가득 / OHT 포화 | `STRATE...STORAGE_UTIL`, `QUE.OHT.OHTUTIL` | STB≥99.3%, OHT≥95% |
| **SLA** 4분초과 | 4분 넘게 못 옮긴 짐 비율 | `QUE.ALL.TRANSPORT4MINOVERRATIO` | ≥ 14% |
| **Sorter** | 분류기 대기 LOT | `SORTER.ABN.SORTERWAITCOUNTOVER` | LOT 대기 |
| **MAXCAPA** | 운영자 CAPA 변경 감지 | `QUE.CNV.3F_CNV_MAXCAPA` | 변경 시 |

> **컬럼 읽는 법**: `영역.분류.세부.지표` 예) `M16HUB.QUE.ALL.CURRENTQCNT` = M16HUB 의 큐(QUE) 전체(ALL) 현재 반송 대기 수.

## 1-3. 고도화 핵심 — LLM 활용 규칙 자동 생성

기존: 사람이 임계·조건 수동 정의 → 누락·튜닝 비용 큼.
**v6: LLM 이 Star 데이터 패턴을 학습해 규칙을 자동 생성** → 사람은 검토·승인만.

```
[Star 데이터 255 컬럼]  →  LLM 패턴 학습  →  [8영역 × 9룰 자동 생성]
```

## 1-4. ★ 실사례 — 2026-05-25 16:57 (실제 Star 데이터)

같은 분의 8영역 룰을 평가한 결과:

| 시각 | 반송큐 | 반송시간(R-A) | STB저장(R-D) | OHT(R-D) | 판정 |
|---|---|---|---|---|---|
| 16:50 | 1,199 | 13.2분 🔴 | 99.4% 🔴 | 91% | 신호 시작 |
| 16:53 | 1,256 | 12.2분 🔴 | 99.4% 🔴 | 90% | 누적 |
| **16:57** | **1,312** | **13.7분 🔴** | **99.4% 🔴** | 91% | **★ 위험 확정** |
| 17:01 | 1,318 | 19.0분 🔴 | 99.4% 🔴 | 89% | 지속 |

# 📊 장표 2. 큐브 파서 + 예측 결과 (언제 맞췄나)

## 2-1. 입력 — 큐브 메시지 통째로 투입

```
구간: 2026-05-25  16:00 ~ 22:00  (큐브 메시지 수십 건)
16:14 "6AFS6201 IN 늘고 있는데요 ERROR있나요?"
18:34 "Deadlock 으로 인해 OHT 정체중입니다."        ← 운영자 인지
19:59 [봇] "M16HUB.QUE.ALL.CURRENTQCNT 2007 >= 2000" ← 시스템 RED 알람
20:16 "M16A Storage full ..."
... (CAPA변경·일반대화 다수 섞임)
```

## 2-2. 큐브 파서 — 같은 장애를 Episode 로 묶기

LLM 파서가 메시지를 **장애 단위로 자동 분류**:

| Episode | 시작~종료 | 유형 | 비고 |
|---|---|---|---|
| **E1** | 18:34~22:15 | 정체·병목 (M16A/HUB) | "Deadlock"→"full"→"불안정" 묶음 |
| 제외 | 17:04, 18:39 ... | CAPA변경 | 운영자 조치 → 정답 제외 |
| 제외 | "STK 이상없음" 등 | normal | 일반 대화 |

> 메시지 수십 건 → **실제 장애 Episode 1건** (정답). 거품 제거.

## 2-3. ★ 예측 결과 — 룰베이스가 언제 맞췄나 (핵심)

| 구분 | 시각 | 내용 |
|---|---|---|
| 🟢 **룰베이스 예측** | **16:57** | Star 데이터로 위험(162) 확정 |
| 🟡 운영자 인지 (큐브) | 18:34 | "Deadlock OHT 정체중" |
| 🔴 시스템 RED 알람 | 19:59 | 큐 2007 ≥ 2000 |

```
16:57 ───────── 18:34 ───────────── 19:59
룰베이스         운영자 채팅         시스템 알람
예측 ★           (+1시간 38분)       (+3시간 2분)
```

> **룰베이스가 운영자보다 1시간 38분, 시스템 알람보다 3시간 2분 먼저 예측.**

## 2-4. 최종 목적 — 룰베이스와의 시너지

```
[큐브 메시지] ─파서─▶ Episode 정답(18:34 정체)
                          │ 그 시각 매칭
                          ▼
            [Star 데이터: 16:57 이미 STB 99.4%/반송 13.7분]
                          │ "정답일 때 메트릭은 이랬다"
                          ▼
            [LLM 룰베이스] 그 패턴 학습 → 더 일찍·정확히 잡도록 고도화
```

| 단계 | 이 사례 |
|---|---|
| 큐브 파서 → 정답 | 18:34 정체·병목 Episode (거품 제거) |
| Star 데이터 매칭 | 16:57 부터 STB 99.4%·반송 13.7분 실측 |
| 룰베이스 검증 | **시스템 알람보다 3시간 먼저** 예측 확인 |
| 고도화 | LLM 이 "정답 직전 패턴" 학습 → 규칙 정교화 |

> **결론**: 큐브 파서가 만든 정답(Episode) + Star 데이터 = 룰베이스가 **시스템 알람보다 3시간 먼저** 정체를 예측함을 실증. 이 정답지로 룰베이스를 지속 고도화.
