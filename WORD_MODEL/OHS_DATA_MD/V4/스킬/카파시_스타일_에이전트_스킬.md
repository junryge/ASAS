## Lecture 0 — 우리가 무엇을 보고 있는가

반도체 FAB 의 **반송 시스템 (OHS)** 이다. FOUP (웨이퍼 통) 이 OHT (Overhead Transport, 천장 레일 위 무인 운반체) 를 타고 장비에서 장비로 이동한다. 그 중심 허브가 **M16HUBROOM** 이다. M14 와 M16 의 모든 FOUP 이 이 허브를 지나간다.

이 허브가 막히면? 전체 라인이 정체된다. 그래서 룰베이스의 목표는 단순하다:

> **"M16HUB 가 막힐 징조를 매분 매분 잡아라."**

전부 그것이다. 다른 모든 건 부산물이다.

## Lecture 1 — 왜 8 영역인가

먼저 영역 (`AREAS_ALL`):
```
M16HUB, M14, M14B, M16A, M16B, M16, M16_PKT, M16_WT
```

왜 8개? 다음과 같이 묻자 — **각 영역이 M16HUB 에 어떻게 영향을 주는가?**

| 영역 | M16HUB 와의 관계 | 신호 |
|---|---|---|
| M16HUB | 본인 | 직접 측정 |
| M14 | M14A 3F → HUB (CNV 4AFC3201/3301) | 인플로 |
| M14B | M14B 7F → HUB (4ABLD 리프터 6대) | 인플로 |
| M16A | HUB ↔ M16A 6F (6ABL60~ 리프터) | 양방향 |
| M16B | HUB → M16B 10F | 아웃플로 |
| M16 | M16 종합 (BACK PRESSURE) | 종합 |
| M16_PKT | M16 패킷 반송 | 보조 |
| M16_WT | M16 → M16WT (WIS STK 경유) | 아웃플로 |

→ 8 영역은 **M16HUB 를 둘러싼 8 방향의 trade-off** 다. 외워야 할 게 아니라 **지도** 다.

## Lecture 2 — 정체란 무엇인가? (3 가지 시각)

같은 정체를 3가지로 볼 수 있다:

### 시각 (a) — **시간이 늘어남** → R-A

> "FOUP 1개를 옮기는 데 평소 3분이면 됐는데, 지금 9분 걸린다."

측정: `AVGTOTALTIME1MIN` (또는 `AVGLOADTIME1MIN`)

영역마다 baseline 이 다르니 임계도 다르다 (`TH_RA`):
```python
TH_RA = {
    'M16HUB':  9.0,   # 허브는 본래 느림
    'M14':     3.3,
    'M14B':    5.0,
    'M16A':    3.2,
    'M16B':    3.5,
    'M16_PKT': 7.5,
    'M16_WT':  2.8,
}
```

여기서 잠깐 — 한 번 9분 찍었다고 정체일까? 측정 노이즈일 수도 있다. 그래서 2가지를 본다:

1. **순간 (RA)**: 최근 10분 중 1회라도 ≥ TH_RA → `ra_trig`
2. **지속 (RA_sus)**: 최근 5분 중 3회 이상 ≥ (TH_RA × 0.67) → `ra_sustained`

`TH_RA_SUSTAINED_RATIO = 0.67`, `TH_RA_SUSTAINED_COUNT = 3` 이 그 정의다.

지속 임계가 절대 임계보다 낮은 이유? **"9분 한 번"보다 "6분이 3번"이 더 무섭다.** 9분은 일시적 spike 일 수 있지만, 6분이 3번이면 만성 정체다.

### 시각 (b) — **큐가 쌓임** → R-B

> "처리량은 같은데 들어오는 게 더 많다. 큐가 늘어난다."

측정: 영역별 큐 (`RB_COL`)
```python
RB_COL = {
    'M16HUB':  'M16HUB.QUE.M14TOM16.MESCURRENTQCNT',
    'M14':     'M14.QUE.ALL.3F_TO_HUB_JOB',
    'M14B':    'M14B.QUE.ALL.7F_TO_HUB_JOB',
    'M16A':    'M16A.QUE.ALL.6F_TO_HUB_JOB',
    'M16B':    'M16B.QUE.ALL.10F_TO_HUB_JOB',
    'M16':     'M16.QUE.SFAB.SENDQUEUETOTAL',
}
```

여기도 2가지 시각:
1. **30분 누적 (RB)**: 30분 전 대비 +N 이상 — **느린 데드락**
2. **10분 폭주 (RB_fast)**: 10분 전 대비 +(N × 0.3) 이상 — **갑작스런 사고**

```python
TH_RB_30 = {'M16HUB': 100, 'M14': 80, 'M14B': 150, 'M16A': 80, 'M16B': 30, 'M16': 20}
TH_RB_10 = {k: max(10, int(v * 0.3)) for k, v in TH_RB_30.items()}
```

왜 30/10 두 윈도우? **다른 종류의 사건을 다르게 잡는다.** 점진적 누적과 폭증은 원인이 다르고 대응도 다르다. 같은 룰로 못 잡는다.

M14B 가 +150 으로 가장 큰 이유? M14B 는 평소부터 큐가 큰 영역이라 baseline 이 다르다. 작은 변동은 정상.

### 시각 (c) — **흐름 패턴이 깨짐** → R-C, R-Flow

> "총 큐는 그대로인데, 흐름의 모양이 이상하다."

**R-C (반전)** — M16HUB 리프터 10대:
```python
LIFTER_IDS = [
    '6ABL6011', '6ABL6012', '6ABL6021', '6ABL6022',  # M16A 6F 대응
    '6ABL6031', '6ABL6032',                          # M16A 3F 대응
    '6ABL0111', '6ABL0112', '6ABL0121', '6ABL0122',  # M16EUV 대응
]
```

20분 전과 비교했을 때 **합계는 줄었는데** (즉 일부 리프터 큐가 빠짐), **다른 리프터 큐는 늘어났다면** → 흐름이 한쪽으로 쏠리고 있다는 신호.

```python
out['rc_trig'] = out['rc_trend'] < 0 and out['rev_count'] >= TH_RC_REVERSE  # 2대
```

**M14 CNV 편향** — 북측 (4AFC3301) 과 남측 (4AFC3201) 비율:
```
if max(north, south) / (north + south) >= 0.70:
    rc_trig = True
```

70% 가 한쪽에 쏠리면 → 다른 쪽 CNV 가 막혔거나, 한쪽이 폭주.

**R-Flow** — 영역간 흐름 노드 10개:
```python
FLOW_NODES = {
    'M14_CNV_TO_HUB':            ('M14',    ...),
    'M14_TO_HUB_JOB':            ('M14',    ...),
    'M14B_7F_TO_HUB':            ('M14B',   ...),
    'M14B_LFT_4ABLD_SUM':        ('M14B',   ...),  # 4ABLD 6대 합
    'M14B_LFT_4ABLD_TO_HUB_SUM': ('M14B',   ...),  # 하강만 합 ★
    'M16A_6F_TO_HUB':            ('M16A',   ...),
    'M16A_2F_TO_HUB':            ('M16A',   ...),
    'M16B_10F_TO_HUB':           ('M16B',   ...),
    'HUB_OHT_QCNT':              ('M16HUB', ...),
    'M14_TO_M16':                ('M16HUB', ...),
}
```

각 노드를 baseline 대비 ratio 로 본다:
- ≥ **1.5** (`TH_FLOW_X1_5`) → 주의 (+5점)
- ≥ **2.0** (`TH_FLOW_X2_0`) → 위험 (+15점)
- ≥ **3.0** (`TH_FLOW_X3_0`) → 심각 (+30점)

→ "평소 X 였는데 지금 3X 라면, 평소 X 가 무엇이었는지에 상관없이 이상하다." 단순한 1차 원리.

## Lecture 3 — 공간이 부족한 경우 (R-D)

지금까지 "시간/큐/흐름" 만 봤다. 한 가지 더 — **저장 공간** 자체가 문제일 때.

**R-D Fab 적체**:
```python
TH_RD_FABSTORAGE = 25.0    # M16HUB.STRATE.ALL.FABSTORAGERATIO
TH_RD_HUB_STB_UTIL = 99.0  # M16HUB.STRATE.STB.3F_STORAGE_UTIL
TH_RD_OHT_UTIL = 95.0      # *.QUE.OHT.OHTUTIL (다른 영역)
```

- M16HUB: FABSTORAGE ratio ≥ 25% OR STB 사용률 ≥ 99% → 신규 FOUP 못 받음
- 다른 영역: OHT 가동률 ≥ 95% → 더 못 옮김

**왜 99% 인가?** 100% 가 아니라? 측정 노이즈 + 마지막 1대 공간이 의미가 있어서. 99% 가 사실상 "꽉 찼다" 다.

**왜 OHT 95%?** OHT 는 100% 가능한 시스템이지만, 95% 넘으면 신규 작업 받을 여유가 없어진다 — 큐가 쌓이기 시작하는 시점.

## Lecture 4 — SLA 와 Sorter (후행 지표)

이 둘은 **이미 사건이 진행된 후** 나오는 신호다. 그래서 정체 예측보다는 **확인** 용.

### SLA — 4분 이상 지연된 FOUP 비율
```python
TH_SLA_RATIO = {'M16HUB': 5.0, 'M14': 25.0, 'M16A': 13.0, 'M16B': 18.0}
```

영역별 임계가 다른 이유? **M16HUB 는 4분이 long-tail 이지만, M14 는 4분이 평범하다.** 영역 특성.

또는 `TRANSPORT4MINOVERCNT` 가 10분 전 대비 +20 이상 증가 — 점진적 SLA 위반 누적.

### Sorter — 공정 시작점의 대기 큐
```python
TH_SORTER_WAIT = {
    'M14': 100, 'M14B': 75, 'M16A': 180, 'M16B': 90, 'M16HUB': 30,
}
TH_SORTER_TRANSFER_FAIL = 1
```

소터는 FOSB → FOUP 변환 장치. 대기 큐가 많다 = 후속 반송이 많이 정체됐다는 **후행 결과**. M16A 가 180 으로 가장 큰 이유? 평소부터 처리량이 많다.

`SORTERTRANSFERFAIL` 은 M16A/M16B 만 있는 컬럼 — 1회만 발생해도 알람 (`TH_SORTER_TRANSFER_FAIL = 1`).

## Lecture 5 — 운영자가 손댄 흔적 (MAXCAPA + MLUD)

엔지니어가 정체 직전이면 어떻게 하는가? **MAXCAPA 를 낮춘다.** 들어오는 FOUP 수를 줄이는 것이다.

이건 정체 그 자체가 아니라 **운영자가 사건을 인지하고 대응 중**이라는 신호다. 그 자체로 위험 score 에 가산.

### MLUD — 또 하나의 운영자 손길

M16HUBROOM 에는 **MLUD** (FIO 6FIOB103/105/107) 가 있다. 도메인 5-2:
> 상황에 따라 M14A 의 FOUP 을 사람이 M16 HUBROOM MLUD 에 투입하거나, VHL 이 운송하여 M16 HUBROOM MLUD 에서 나온 FOUP 을 M14A 로 직접 운반.

→ MLUD 는 OHT 가 정체일 때 사람이 직접 옮기는 backup 채널. MLUD 큐 (`M16HUBTOM14MANUAL_CURRENTQCNT`) 가 늘어남 = "OHT 로 못 옮기는 게 많아서 수동 우회 중" 이라는 강한 사건 신호. 운영 메신저 단골:

> "MLUD 도 밀리고있는데", "M16Bridge MLUD에서 풉 출고가 원활하지않고"

```python
MAXCAPA_NORMAL = {
    'M16HUB.QUE.LFT.3F_LFT_MAXCAPA':       (165, 100),
    'M16HUB.QUE.LFT.3F_M14BLFT_MAXCAPA':   (66, 50),
    'M16HUB.QUE.CNV.3F_CNV_MAXCAPA':       (129, 80),
    'M14.QUE.CNV.3F_CNV_MAXCAPA':          (244, 150),
    'M16A.QUE.LFT.2F_LFT_MAXCAPA':         (54, 40),
    'M16A.QUE.LFT.6F_LFT_MAXCAPA':         (149, 100),
}
```

각 `(정상값, 임계)`. 임계 이하 → 운영자가 줄여놓은 상태 → 사건 진행 중.

룰 점수: **MAXCAPA*n** = `10 × n` (변경된 컬럼 개수만큼).

## Lecture 6 — 어떻게 합치는가 (Score Aggregation)

지금까지 본 모든 신호를 **하나의 숫자** 로 만든다.

### Step 1 — 영역별 점수 (0~50)

각 영역마다 8 영역 다 본다. 각 영역에서:
| 시그널 | +점수 |
|---|---|
| **RA** | +10 |
| **RA_sus** | +5 |
| **RB** | +10 |
| **RB_fast** | +5 |
| **RC** | +8 |
| **RD** | +7 |
| **SLA** | +5 |
| **SORT** | +3 |
| **MAXCAPA*n** | +10n |

→ `area_score` (최대 50, 클리핑)

### Step 2 — Unified Score (0~500)

```
unified_risk_score = Σ area_score      (8영역 합산 = layer1_total)
                   + Σ flow_score      (10 노드, 주의+5/위험+15/심각+30)
                   + Σ sla_score       (영역별 +5)
                   + Σ sorter_score    (영역별 +3)
                   + Σ maxcapa_score   (변경 1개당 +10)
```

최대 500 으로 클리핑.

### Step 3 — 6 등급 분류

```python
if unified_risk_score >= 250:  level = '매우위험'
elif >= 150:                   level = '위험'
elif >= 80:                    level = '주의'
elif >= 65:                    level = '경계'
elif >= 30:                    level = '관심'
else:                          level = '정상'
```

**왜 6 등급?** 4 등급이면 너무 거칠고, 10 등급이면 운영자가 못 외운다. 6 등급이 실용적 sweet spot.

**왜 임계 30/65/80/150/250?** 데이터 분포 (p95/p99) 와 운영자 인지 가능성을 동시 고려.

## Lecture 7 — Stage 판정 (사건 정의)

위 score 는 **정도** 다. Stage 는 **사건 발생 여부** 다.

```python
unified_s1 = any_ra OR any_ra_sustained          # 조기경보
unified_s2 = any_rb                              # 주의보
unified_s3 = any_ra
             AND (any_rd_or_sla OR any_rc)
             AND (any_rb OR any_flow_severe)     # ★ 확정
```

**S3 의 3중 조건이 핵심이다.** 단일 룰 1개로 사건 확정 안 한다 — 위양성 너무 많아짐. 3종류가 동시 발동해야 한다:

1. 시간 지연 (RA) — 정체가 측정됨
2. 공간/SLA/흐름 (RD or SLA or RC) — 원인 후보 존재
3. 누적 (RB or flow severe) — 실제로 큐가 쌓임

→ **3 시각 모두에서 일치할 때만 확정.** 룰 엔지니어링의 정수.

STAGE_LABEL = `{0: '이벤트없음', 1: '1단계 조기경보', 2: '2단계 주의보', 3: '3단계 ⭐확정'}`

## Lecture 8 — 핫스팟 (Hot Area)

"어느 영역이 가장 위험한가?" — `area_score` 가 최대인 영역.

```python
hot_area, hot_score = argmax(area_results, key='area_score')
```

운영자에게 "지금 M14B 부터 봐라" 라고 짚어주는 역할.

**triggered_areas**: `area_score ≥ 15` 인 모든 영역. 이게 곧 영향 영역 (`affected_areas`).

**propagation_chain**: 어느 영역이 먼저 발동했고, 어느 순서로 퍼졌는가. 60분 lookback (`PREDICT_LOOKBACK_MIN = 60`).

## Lecture 9 — M14B 4ABLD 리프터 (도메인 4-4 + 보강)

도메인 명세 (4-4):
> M14B(7F) 와 M16HUBROOM(3F) 은 LFT 로 연결. 리프터명 **4ABLD** 로 시작.

6대: 4ABLD111, 4ABLD112, 4ABLD121, 4ABLD122, 4ABLD131, 4ABLD132.

### 옛 룰의 한계
초기 룰은 4ABLD122 만 봤다. 운영 메신저에서 "4ABLD122 Auto Up" 같은 표현이 가장 자주 나왔기 때문이다.

문제: **5대가 막혀도 122 가 정상이면 룰이 놓친다.**

### 보강 (현재)

```python
'lft_4abld_sum':         sum(6대의 TOTAL_CURRENTQCNT)
'lft_4abld_to_hub_sum':  sum(6대의 7F_TO_4F_CURRENTQCNT)   ← M16HUB 방향만
'lft_4abld122':          단독 (메신저 호환용)
```

왜 `to_hub_sum` 도 별도? **7F→4F (하강) 가 M16HUB 정체에 직접 영향.** 4F→7F (상승) 은 M14B 내부 이동이라 무관.

데이터로 보면 둘이 매우 다르다:
```
양방향 TOTAL = 7+8+5+4+4+3 = 31
하강만       = 4+5+2+2+3+2 = 18   ← 이게 진짜 정체 신호
```

ML 학습 결과도 121/122 둘 다 상위 피처로 자동 선택 — 도메인 지식과 데이터 일치.

## Lecture 10 — 사건 추적 FSM (시간 차원)

매분 stage 판정만 하면 부족하다. 사건은 **시작과 끝** 이 있다.

```
event_start = stage가 1+ 로 진입
event_end   = stage가 0 으로 복귀 + 10분 추가 대기 (INCIDENT_END_GAP_MIN)
```

10분 gap 두는 이유? Stage 가 잠깐 떨어졌다가 다시 올라가는 일이 흔하다 (FOUP 이 잠시 빠지면). 진짜 종료는 10분간 안 올라와야 인정.

사건 단위 출력 (`사건단위.csv`):
- 시작/종료 시각
- max_risk_score / level
- 핫 영역
- triggered_rules (어느 룰이 발동했는지)
- risk_factors (핵심 위험요인)
- maxcapa_changes (사건 중 운영자 변경 컬럼)
- relation (영역별 컬럼-값-임계 상세)

## Lecture 12 — 정체 유형 분류 (실전)

이제 매분 들어오는 발동이벤트 한 행을 보면서 **어떤 유형의 정체인가** 답해야 한다.

답하는 순서:

```
Q1. unified_risk_score < 30?         → 정상 통과
Q2. ≥ 30 이면 stage 는?               → 0/1/2/3
Q3. hot_area 는?                     → 어느 영역인가
Q4. M16HUB_signals (또는 hot_area의 signals) 는?
    └─ RA?      → 시간 지연  → 유형 1
    └─ RB?      → 큐 누적    → 유형 2
    └─ RC?      → 흐름 반전  → 유형 3
    └─ RD?      → 공간 부족  → 유형 4
    └─ SLA?     → 후행 SLA    → 유형 6
    └─ SORT?    → 후행 소터  → 유형 7
    └─ MAXCAPA? → 운영자 변경 진행 중
Q5. flow_signals 가 비어있지 않으면 → 유형 5 (영역간 흐름)
Q6. 유형이 여러 개 동시 발동? → 핫 영역의 1순위 + S3 확정 여부 같이
```

대응 SOP 는 `일반_에이전트_스킬.md` 의 유형 1~7 섹션 참조. 본 문서는 **왜 그렇게 분류하는가** 에 집중한다.
